# 面试讲解与可能问答

## 30 秒介绍

“ForgeLite 把 coding agent 拆成模型规划和本地执行两层。模型通过原生 tool calling 选择读、写、替换或运行命令；我用 Python 标准库自己解析这些调用，并在固定工作区执行，再把结果回传模型，直到模型给出最终文本或达到回合上限。它不依赖任何 agent 框架。为了控制上下文，我做了时间历史压缩和按最近访问淘汰的 LRU 工作记忆。”

## 可能问题

**模型为什么需要 tool calling，而非让它输出 shell 文本？**

tool calling 给每个操作明确的名称和 JSON 参数 schema。程序可以逐项校验、记录 `tool_call_id` 并回传对应结果，模型也更容易在失败后修正。文本解析则容易混淆解释、代码块和命令。

**如何保证模型不会访问工作区外的文件？**

先把工作区和请求路径都做 `resolve()`，再用 `candidate.relative_to(root)` 判断祖先关系。绝对路径、空路径和 `../` 穿越会返回错误。这个检查在真正每一个文件工具内执行，不依赖模型遵守 prompt。

**命令工具安全吗？**

它提供的是降低误操作风险的工程约束，并非安全隔离：工作目录固定、命令输出和时间有限制、明显灾难性模式会拦截。但 shell 本身能力很强，恶意模型仍不应被授予生产机权限。因此实际使用必须给 disposable workspace，并可进一步改为容器/权限受限子进程。

**上下文压缩为什么还需要 LRU？**

历史压缩解决“很早以前发生什么”；LRU 解决“现在最可能继续使用什么”。编码任务常反复修改少量文件，LRU 用文件路径作为 key 刷新访问时间，容量满时删最久未用项。它保存短观察而不是完整文件，降低 token 占用；最终编辑前再读文件保证正确性。

**什么时候停止？如果模型一直调用工具怎么办？**

无 tool call 且有 assistant 文本时正常结束；达到 `max_steps` 时硬停止并说明可能有部分改动。网络、参数或工具错误以 tool result 送回模型，使模型通常能调整下一步，而不是让程序异常退出。

**如何证明不是封装现成 agent？**

可从 `src/coding_agent` 逐个展示：`client.py` 用 `urllib` 发 HTTP，`agent.py` 是显式 while/for 控制循环，`tools.py` 是全部本地工具，`history.py` 与 `lru_memory.py` 是自主上下文管理。依赖列表也只有打包工具，没有 agent 框架或 SDK。
