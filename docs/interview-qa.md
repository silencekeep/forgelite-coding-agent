# 面试讲解与可能问答

## 30 秒介绍

“ForgeLite 把 coding agent 拆成模型规划和本地执行两层。模型通过原生 tool calling 选择读、写、替换或运行命令；我用 Python 标准库自己解析这些调用，并在固定工作区执行，再把结果回传模型，直到模型给出最终文本或达到回合上限。它不依赖任何 agent 框架。为了控制上下文，我做了时间历史压缩和按最近访问淘汰的 LRU 工作记忆。”

## 可能问题

**模型为什么需要 tool calling，而非让它输出 shell 文本？**

tool calling 给每个操作明确的名称和 JSON 参数 schema。程序可以逐项校验、记录 `tool_call_id` 并回传对应结果，模型也更容易在失败后修正。文本解析则容易混淆解释、代码块和命令。

兼容网关偶尔会省略 call ID，或把 arguments 直接给成对象。解析层会为前者生成仅用于本地历史的稳定 ID，把后者序列化为标准 JSON 文本；无法安全解释的 tool call 则明确失败，不让畸形消息污染后续上下文。

**如何保证模型不会访问工作区外的文件？**

先把工作区和请求路径都做 `resolve()`，再用 `candidate.relative_to(root)` 判断祖先关系。绝对路径、空路径和 `../` 穿越会返回错误。这个检查在真正每一个文件工具内执行，不依赖模型遵守 prompt。

**原子写为什么不用固定的 `.tmp` 文件？**

固定临时名可能与残留文件冲突，更严谨地说，还可能被预先布置成链接。ForgeLite 用 `NamedTemporaryFile(delete=False)` 在目标目录独占创建随机名称，关闭句柄后用 `os.replace` 原子覆盖；失败路径会清理该临时文件。目标路径及其父目录仍先经过工作区边界解析。

**命令工具安全吗？**

它提供的是降低误操作风险的工程约束，并非安全隔离：工作目录固定、命令输出和时间有限制、明显灾难性模式会拦截。但 shell 本身能力很强，恶意模型仍不应被授予生产机权限。因此实际使用必须给 disposable workspace，并可进一步改为容器/权限受限子进程。

**上下文压缩为什么还需要 LRU？**

历史压缩解决“很早以前发生什么”；LRU 解决“现在最可能继续使用什么”。编码任务常反复修改少量文件，LRU 用文件路径作为 key 刷新访问时间，容量满时删最久未用项。它保存短观察而不是完整文件，降低 token 占用；最终编辑前再读文件保证正确性。

**什么时候停止？如果模型一直调用工具怎么办？**

无 tool call 且有 assistant 文本时正常结束；达到 `max_steps` 时抛出专用异常并说明可能有部分改动，CLI 返回非零、Web 返回 422，自动化不会把它误判为成功。网络、参数或工具错误以 tool result 送回模型，使模型通常能调整下一步，而不是让程序异常退出。真实大目录测试还发现模型可能重复递归列目录，因此列表现在默认浅层；若连续重复完全相同的只读调用且中间没有写入或命令，工具会明确要求缩小路径或改用 `search_text`。

**为什么任务和读取输出还要限长？**

上下文压缩是近似字符预算。如果当前任务本身无限长，Low 档可能在第一次请求前就只能把它压成摘要；所以任务统一限制为 16,000 字符。单文件允许检查到 200 KB，但一次 `read_file` 最多回传 30k 字符，并提示按行继续。这样既能处理较大文件，又不会让一次工具结果挤掉当前目标和最近操作。

**为什么新增 `search_text`，直接让模型反复 `read_file` 不行吗？**

定位一个类或符号时，递归列目录再整文件读取会快速消耗上下文。`search_text` 在本地做 UTF-8 字面量搜索，可限定相对路径、文件 glob、大小写与最大结果数，并跳过大文件、二进制文件、依赖目录及指向工作区外的链接。一次真实 Web 验收中，模型用它定位 `TOOL_SCHEMAS` 后只读必要源码，3 回合准确列出 6 个工具。

**如何证明不是封装现成 agent？**

可从 `src/coding_agent` 逐个展示：`client.py` 用 `urllib` 发 HTTP，`agent.py` 是显式 while/for 控制循环，`tools.py` 是全部本地工具，`history.py` 与 `lru_memory.py` 是自主上下文管理。依赖列表也只有打包工具，没有 agent 框架或 SDK。

**你如何验证 agent 可以从空目录完整交付，而不是只会修改已有代码？**

我有三层证据。第一层是不联网的端到端控制循环测试：模拟模型依次请求写实现、写测试、写 README、运行 unittest，验证本地工具编排。第二层是真实 `openai/gpt-oss-120b` 的 7 回合无内容审计：从空目录创建项目，第一次命令失败后下一回合自行修正。第三层是实际生成文本的 SHA-256 快照和独立复验：5 项测试及 add/list/done 黑盒操作通过，错误 ID 返回非零。三者分别证明“框架能编排”“真实模型确实行动”“最终产物确实工作”，视频也使用这次结果。

**真实演示中有失败吗？为什么这反而重要？**

有。第一次 `run_command` 返回 `ok=false`，控制循环没有崩溃，也没有把失败当成功，而是把工具错误作为对应 `tool_call_id` 的结果回传。模型下一回合改变命令并得到 `ok=true`。这证明 agent 是“观察—行动—反馈—修正”的闭环，而不是一次生成固定脚本。

**为什么本地网关要特殊处理代理？**

桌面系统可能全局设置 `HTTP_PROXY/HTTPS_PROXY`。普通 `urllib` 会继承它，导致 `127.0.0.1` 请求错误地送往代理并返回 502。客户端解析 base URL；只有 `localhost`、IPv4/IPv6 loopback 使用空 `ProxyHandler` 直连，远程 API 仍服从系统网络配置。这个判断有独立单测。

**历史压缩怎样保证 API 消息仍合法？**

不能按单条消息粗暴切片，因为可能保留 `role=tool` 却删掉引入它的 assistant `tool_calls`。ForgeLite 把一条工具调用消息和后续全部工具结果组成原子组，再按组选择最近历史；测试会检查任何保留的 `tool_call_id` 都有对应父调用。

**Low、Medium、High 是不是只改了 UI 标签？**

不是。三档分别设置不同的本地 system instruction、默认最大模型回合与上下文字符预算；显式 `--max-steps` 或环境变量仍可覆盖。Web 控制台的腕表选择会把同一个值传给 `AgentConfig`，测试断言 High 确实得到 28 个默认回合。这样实现不依赖某个厂商专有的 `reasoning_effort` 参数，在 OpenAI 兼容网关间更可移植。

**为什么还做 Web 控制台，它会不会变成“只封装一个界面”？**

Web 是可选适配层，核心 CLI 和 `CodingAgent` 完全不依赖它。浏览器只提交任务与思考档位；服务器仍在本地创建同一个 `CodingAgent`，工具、循环、上下文和安全边界全部是本项目代码。它固定监听 loopback、固定工作区、限制请求体和任务长度，并用锁拒绝并发修改，因此展示效果没有扩大远程权限。新增的 NDJSON 端点只是把 `audit_sink` 事件逐行刷新给浏览器，不接管 agent 决策。

**界面里的 ReAct Reason 是模型思维链吗？**

不是。ForgeLite 能诚实证明的是“第几次模型请求正在规划”，不能也不应该声称拿到了模型的隐藏思维链。Act 来自可解析的原生 tool call，Observe 来自本地工具的真实结果；Reason 只显示轮次和压缩后消息数。这样既能展示 ReAct 闭环，又不会伪造推理内容或把敏感 prompt 放进视频。

**审计日志为什么不直接保存完整 prompt 和命令输出？**

完整内容更容易复盘，但可能包含源码、业务数据或密钥。`--audit-log` 只保存 UTC 时间、事件名、工具名、参数键、成功状态、输出长度和终止原因；足以重建执行流程，同时降低视频和日志泄密风险。
